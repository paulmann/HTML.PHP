# Internationalisation (i18n) Guide

The engine ships a complete gettext-compatible translation layer: PO/MO
catalogues, plural-form rules, message contexts, text domains, fallback
chains, Accept-Language negotiation and interpolation — plus first-class
integration with the legacy `@{KEY}` template syntax and with WordPress.

## 30-second tour

```php
require 'php83/html.php';

// 1. Load catalogues (file or directory; .po and .mo both supported).
html_load_translations('de_DE', __DIR__ . '/languages', 'myapp');
html_load_translations('ru_RU', __DIR__ . '/languages', 'myapp');

// 2. Choose the locale (manually or from the browser).
html_set_locale(html_detect_locale(
    ['en', 'de_DE', 'ru_RU'],
    $_SERVER['HTTP_ACCEPT_LANGUAGE'] ?? null
));

// 3. Translate.
echo html_t('Hello, {name}!', ['name' => 'Welt'], 'myapp');
echo html_n('%d day', '%d days', 3, [3], 'myapp');   // "3 Tage"
echo html_x('Book', 'verb', [], 'myapp');            // "Buchen"
```

## Catalogue files

Directory layouts recognised by `html_load_translations($locale, $path, $domain)`:

```text
languages/                       languages/
├── myapp-de_DE.mo   ← preferred └── de_DE/
├── myapp-de_DE.po                   └── LC_MESSAGES/
├── de_DE.mo                             └── myapp.mo
└── de_DE.po
```

A direct path to a single `.po`/`.mo` file also works; the format is
sniffed by magic bytes, not extension.

**PO** support: `msgctxt`, `msgid`, `msgid_plural`, `msgstr[n]`, multi-line
strings, `#`/`#.`/`#:`/`#|` comments, `,fuzzy` flag (fuzzy entries are
ignored), `Plural-Forms` and `Content-Type` headers. Non-UTF-8 charsets are
converted via iconv/mbstring when available.

**MO** support: little/big endian, revisions 0–1, context separator `\x04`,
NUL-separated plural forms, bounds-checked tables (truncated/hostile files
are rejected with a `catalog-parse` diagnostic, never a warning).

## Plural forms

The `Plural-Forms` header expression is evaluated by a **safe arithmetic
parser** (`HtmlPhp\I18n\PluralForms`) — integer arithmetic over `n`,
comparisons, `&&`, `||`, `!`, `?:`, parentheses. No `eval()`. Results are
clamped to `nplurals` (hard cap 6).

When a catalogue has no header, built-in rules for 60+ languages apply
(language key of the active locale): single-form (ja, zh, ko, vi, …),
two-form Germanic, Slavic three-form (ru, uk, be, bs, hr, sr), Polish,
Czech/Slovak, Lithuanian, Latvian, Romanian, Slovenian, Celtic (ga, gd, cy,
mt), Arabic six-form, Icelandic/Macedonian edge cases.

```php
use HtmlPhp\I18n\PluralForms;

$ru = PluralForms::parse(null, 'ru');
$ru->select(1);   // 0  → "1 день"
$ru->select(3);   // 1  → "3 дня"
$ru->select(12);  // 2  → "12 дней"
```

## Lookup order

`html_t()` / `html_n()` / `html_x()` / `html_nx()` resolve in this order:

1. **WordPress delegation** (when running inside WP; see below) — a hit is
   any result different from the source string;
2. **own catalogues**: the active locale, then each locale of
   `HTML_I18N_FALLBACK` (default `['en']`);
3. **the source string** — never empty, never an exception. With
   `HTML_DEBUG=true` a miss is also recorded in `html_errors()`.

The final text passes through interpolation and the `htmlphp_translate`
filter hook.

## Interpolation

Both styles work, and can be mixed:

```php
html_t('Hello, {name}! You have {count} messages.',
       ['name' => 'Ada', 'count' => 3]);          // named
html_t('%2$s scored %1$d points', [42, 'Ada']);    // positional sprintf
```

Named replacement runs first (`{key}` → value), positional `vsprintf()`
second; a broken format returns the raw translation instead of throwing.

## Templates

The legacy translation syntax consults the catalogues automatically:

```html
<h1>@{Welcome}</h1>            <!-- catalogue → Translate.Welcome global → "Welcome" -->
<p>%{label|translate}</p>      <!-- translate the substituted value -->
```

`Translate.KEY` resolution (both `HTML()` and `html_render()`): catalogue
first, then `$GLOBALS['Translate.KEY']` (so legacy global-based translations
keep working and win over catalogues in the legacy pipeline), finally the
key itself.

## Locale negotiation

```php
html_detect_locale(['en', 'de_DE', 'ru_RU'], 'de-AT,de;q=0.9,en;q=0.8');
// → 'de_DE'   (same language, any territory)
```

Match order: exact normalised tag → same language → configured default.
Normalisation handles `en-us`, `EN_US.utf8`, `de_DE@euro`, script subtags.
Set `HTML_I18N_DETECT=true` to negotiate once automatically on first use
against the locales that have loaded catalogues.

## WordPress integration

Inside WordPress (`ABSPATH` + `__()` detected, or forced via
`HTML_I18N_WP=true`), translations **delegate first** to
`__()`/`_n()`/`_x()`/`_nx()` with your domain — so standard
`load_plugin_textdomain()` catalogues work as usual — and the engine's own
catalogues act as an overlay for misses. `html_wp_boot(['locale' => true])`
(the default) syncs `HTML_I18N_LOCALE` with `determine_locale()`. Set
`HTML_I18N_WP=false` to keep everything inside the engine (useful when the
engine renders outside the WP request cycle, e.g. in CLI jobs).

## Configuration keys

| Key | Default | Purpose |
|---|---|---|
| `HTML_I18N_LOCALE` | `en` | active locale |
| `HTML_I18N_FALLBACK` | `['en']` | fallback chain |
| `HTML_I18N_DOMAIN` | `messages` | default domain |
| `HTML_I18N_DETECT` | `false` | negotiate from Accept-Language on first use |
| `HTML_I18N_WP` | unset (auto) | `true`/`false` force/forbid WP delegation |

## Diagnostics

* `HtmlPhp\I18n\Translator::stats()` — loaded domains/locales/message counts;
* `html_errors('catalog-parse')` — catalogue problems (unreadable, bad MO,
  charset);
* with `HTML_DEBUG=true`, every unresolved message id is recorded.
